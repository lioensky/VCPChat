# 工具循环交接前置闸门

## 目标
避免工具回合结束后后端已向上游发送下一轮请求，前端才中止而产生额外费用。
本期先施工前端；后端尚未实现、联调未完成，不宣称已避免费用。

## 用户确权
- 同一活动请求无论多少条暂挂，只需一份ready。
- 暂挂需求从空变非空时预约；全部撤回且无压缩需求时撤销。
- 请求之间隔离，不采用全局共享ready。
- 工具回执与终稿持久化成功后才压缩、队列入场、启动新请求。

## 状态不变量
- ready是当前请求交接需求的派生状态，不绑定单条消息。
- 需求 = 有效待入场消息 OR 自动压缩需求。
- 撤回清空可以cancel；正式交接消费清空不能恢复旧循环。
- 手动Stop优先；旧代际cancel不得撤销新预约。
- 不把admissionToken假定为requestId；使用网络请求实际messageId。
- 主进程统一持有请求绑定和队列需求，页面切换不影响预约。
- 控制请求不能阻塞中央队列落盘锁；控制网络失败不能误触发本地硬中止。

## 待核实协议

确认方式、交接提交动作与超时策略尚待收敛，不作为已实现契约。

## 待后端实现的明确契约
- 聊天响应需尽早发出响应头 x-vcp-tool-loop-handoff: 1，不能缓冲到工具回合结束才发送。
- 无该响应头的请求不发送预约控制，沿用旧行为。
- POST /v1/interrupt 新增action prepare_handoff / cancel_handoff。
- 控制正文 requestId 为真实messageId，附handoffId和递增revision。
- 控制成功需返回JSON success:true；HTTP成功但缺少明确成功标识也视为未确认。
- cancel匹配对应handoffId；revision用于拒绝迟到的旧状态更新。
- 无action的现有硬中止继续有效，承担最终交接提交及用户Stop。
- 硬中止后的请求不可被迟到prepare/cancel复活；完成请求不可重新登记闸门。
- 工具批次完成后先推完整回执，再在上游下一轮请求派发前执行预约闸门。
- 1至2秒闸门等待及超时策略在后端施工时最终确权；前端目前不依赖新增SSE控制事件。
- 前端控制HTTP超时5秒，非闸门等待时长。
