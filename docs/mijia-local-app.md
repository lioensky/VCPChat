# 米家本地应用（pqylf）

## 入口与宿主

- 右侧工作区「应用」列表 → 在当前窗口的右侧工作区打开米家标签，重复点击激活已有标签。不要转发到主界面标签。
- 主界面 Dock（常用入口与全部应用列表）→ 直接打开独立浮窗。复用已有浮窗并聚焦；不打开顶部标签或聊天浮层，也不先经过右侧工作区。浮窗不以主窗口为 parent，避免主窗口最小化时被系统连带隐藏。
- 一个应用、同一套设备面板与登录服务，宿主只决定挂载位置。其他应用的默认路由不变。
- 沿用现有子应用的 `styles/themes.css` 和主题切换契约；米家专用 CSS 仅负责布局与局部组件样式，侧栏窄宽不横向溢出。

## 登录和设备

- 首次由用户主动点「连接米家」发起扫码；不把二维码写进聊天或应用日志。已有本机登录态直接验证，不重复要求扫码。
- 扫码完成后，用实际调用设备的本机服务读取设备列表；只有云端列表读取通过才显示「已连接」。
- 仅把页面所需数据回传 UI；凭据留在本机调用端，设备身份用 ID 绑定，名称只负责显示。
- 账号连接和设备状态分开：在线不等于已开，单设备读取失败不触发重新登录。
- 已验证：前端 Python SDK `get_devices_list()` 能读取实际设备列表；这不是设备属性读写证明。分布式旧台灯命令不是面板接入的先决条件。

## 验收

分别从右栏与主界面 Dock 点击米家，核对实际宿主与重复打开；切换浅色、深色与自定义主题；用已有登录态加载设备列表，验证两个入口不重复扫码。验证缺失或失效登录态、请求失败和取消扫码后的 UI 状态。

## 设备控制契约

- 信源：`miot-spec.org/miot-spec-v2` 对应型号的 v2 规格；本机 `mijiaAPI 2.0.1` 通过 `get_devices_prop` 按 DID 实读。顶层请求成功不代表每项成功，应按 DID、SIID、PIID 与每项 code 对齐。
- `yeelink.light.lamp2`：2/1 开关、2/2 亮度（1–100%，步进 1）、2/3 色温（2500–4800 K，步进 1）；均读通，规格声明可写，实机写入尚未验证。仅开关即时下发；数值拖动、松手、输入、失焦均不得下发，只有「应用」提交脏字段。
- `midjd6.fridge.610`：3/1、4/1 温区实测温度；3/2、4/2 温区设定温度；2/1 故障码、2/2 模式、5/2 门状态，均读通。首版全部只读，不开放规格声明的可写温度及模式。
- 右栏与浮窗共用能力表和设备写入队列；单个面板的草稿不等于设备真值。刷新保留草稿；撤销只丢弃未提交草稿，不反向写设备。逐项呈现失败或未确认，禁止把整批标成成功。
- 写入边界：主进程校验本地页面来源、参数形状并按 DID 串行调度；Python 桥用米家云实际发现的型号查属性白名单，验证提交方式、类型、范围与步进。未知型号仅展示设备基础信息；页面不能传任意 SIID/PIID。
