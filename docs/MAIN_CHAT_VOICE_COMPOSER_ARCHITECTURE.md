# VCP 语音功能技术设计与架构实现文档

本文档系统性记录主聊天界面语音交互系统的架构设计与实现。

> **架构边界与设计前提**：
> 本工程中，底层 Windows 语音输入引擎（`rust_voice_input_engine`）、独立语音聊天窗口（`Voicechatmodules/voicechat`）以及无痕输入跳板窗口（`Voicechatmodules/voice-input-capture`）均为**原作者的原生架构与代码实现**。
> 本次工作是在**完全尊重原作者已有体系、绝不入侵原有代码结构**的核心前提下，在既有能力之上**额外并联搭建了一条服务于主聊天界面普通输入框的独立交互线**，实现了打字听写（STT）、人声哨兵连续待命（VAD）、原声录音归档（WAV）以及两套系统间的自律避让与资源复用。

---

## 1. 系统整体架构与交互模型

系统呈现“原作者已有体系”与“主聊天并联增强线”两套既独立又协同的语音链路：

```
[用户交互入口]
  ├── [原作者体系] 独立语音聊天小窗口 (VoiceChatWindow)
  │     └── 物理快捷键 (默认 F7) ──> Rust 低级键盘钩子 ──> 系统输入法语音 (Win+H / 右 Alt)
  │
  └── [本次并联线] 主聊天窗口 (MainChatWindow) 输入区
        ├── 麦克风左键点击 ──> 实时语音听写 (STT) ──> 文本实时回填主输入框
        │         └── [空闲待命] ──> 人声哨兵 (VAD) 自动拾音 ──> 循环激活下一轮听写
        └── 麦克风右键点击 ──> 原始语音录音 (WAV) ──> 高通滤波与软噪声门 ──> handleFileDrop 注入附件栏
```

### 1.1 关键交互约束
1. **输入框全局单例**：主聊天界面中，无论是单 Agent 模式还是双 Agent 对话模式，底层的 DOM 节点均为同一个 `#messageInput`。语音模块无需针对不同 Agent 切换重新绑定 DOM，直接操作输入框引用即可。
2. **快捷键与界面按钮严格隔离**：
   - 全局物理快捷键（如 F7）由原作者编写的 Rust 钩子监听，专属于独立语音聊天小窗口（`voiceChatWindow`）；
   - 主聊天窗口界面上的麦克风按钮仅响应鼠标点击或内部人声哨兵（`PassiveVoiceSentinel`）触发，不占用全局物理快捷键；
   - 两者即使同时打开，焦点与操作流也互不干扰。

## 2. 复用原作者底层引擎与跳板机制

为了避免另起炉灶引入庞大冗余的依赖，本次开发最大限度复用了原作者已有的底层跳板设施，仅在接口参数上进行了非侵入式的轻量扩展：

### 2.1 原作者 Rust 后台引擎 (`rust_voice_input_engine`)
- **原生实现**：原作者通过 Windows 底层低级键盘钩子（`WH_KEYBOARD_LL`）监听全局配置的热键（如 F7），并在 Windows 语音键入（Win+H）与输入法语音（模拟长按右 Alt）两种模式下驱动系统输入。
- **并联扩展点（`programmatic` 参数）**：
  原作者原先的逻辑强制要求必须由键盘物理按下（`awaiting_focus`）才允许执行聚焦。为了让主界面按钮的鼠标点击也能安全复用该引擎，仅在 `Command::FocusReady` 指令结构中扩展了一个可选布尔字段 `programmatic: bool`。当来自主界面程序化调用时允许放行，原作者的所有热键监听与原有分支完全保持原貌运行。

### 2.2 原作者隐藏无痕输入跳板窗口 (`Voicechatmodules/voice-input-capture`)
Windows 原生语音输入（Win+H）和第三方输入法在 Electron 复杂 DOM 树中常常无法正确识别文本插入点。原作者设计了专用的跳板窗口 `voiceCaptureWindow`（320x42px，置顶，无边框透明）：
- **聚焦确认机制**：连续调用双重 `requestAnimationFrame` 并附带 120ms 延时，确保 Chromium 渲染流水线与 Windows Text Services Framework (TSF) 完全绑定且光标进入可写状态（`hasWritableSelection`）后，才向 Rust 发送 `focusReady`，避免 Win+H 误报“当前无活动输入区”。
- **轻量协作扩展**：
  在保持原有事件监听不破坏的前提下，在 `compositionend` 与 `onStop` 上报中透传了 `settled: true` 标记，使主进程能够更精准地获知输入法何时真正完成定稿，从而将原本保守的防抖等待时间大幅优化。

## 3. 主聊天语音交互状态机 (`modules/voice/chatVoiceComposer.js`)

前端控制器维护严格的四状态机：

```
                 ┌──────────────┐
                 │     IDLE     │ ◄─────────────────────────┐
                 └──────┬───────┘                           │
            左键点击    │       ▲ 用户再次点击 / 异常       │
                        ▼       │                           │
                 ┌──────────────┴┐                          │
                 │   STT_READY   │                          │
                 └──────┬────────┘                          │
        自动唤醒 / 启动 │       ▲ 会话结束 / 哨兵待命       │
                        ▼       │                           │
                 ┌──────────────┴┐                          │
                 │ STT_RECORDING │                          │
                 └───────────────┘                          │
                        │                                   │
              右键点击  │                                   │
                        ▼                                   │
                 ┌───────────────┐                          │
                 │AUDIO_RECORDING│ ─────────────────────────┘
                 └───────────────┘       录音停止 / 上传完成
```

### 3.1 状态说明
- `IDLE`：麦克风按钮呈常态透明，无任何监听与定时器；
- `STT_READY`：麦克风进入粉色激活态，后台人声哨兵挂起监听；
- `STT_RECORDING`：听写会话执行中，系统跳板窗口处于展示状态，哨兵暂时挂起避免回声；
- `AUDIO_RECORDING`：麦克风进入橙色激活态，正在采集原始音频流。

### 3.2 并发与竞争保护
- **`sessionEpoch` 计数锁**：控制器内部维护自增的 `sessionEpoch`。在所有异步操作（如启动哨兵、调用主进程 IPC）返回后，强制比对 `invokingEpoch === this.sessionEpoch`。若异步等待期间用户已点击退出，立即丢弃过时返回，避免幽灵会话启动。
- **状态迁移统一出口 (`transitionTo`)**：所有状态变更均收拢至单一方法，自动同步麦克风样式、更新悬停提示（Tooltip），并在退出 STT 时彻底销毁哨兵。

## 4. 人声活动检测哨兵 (`modules/voice/passiveVoiceSentinel.js`)

负责在静默期间检测人类发声，免除用户反复点击按钮的操作。

### 4.1 算法流程
1. **音频流初始化**：从 `navigator.mediaDevices.getUserMedia` 获取单声道音频流，经由 `BiquadFilter` 施加 115Hz（Q=0.7071）的高通滤波，滤除桌面敲击低频震动与空调底噪。
2. **时域切帧**：采用 `ScriptProcessor` 获取 256 个采样点的时域数据块。在标准 16000Hz 采样率下，单帧时长精确对应 16.0 毫秒。
3. **动态底噪跟踪**：
   - 逐帧计算均方根能量 $RMS = \sqrt{\frac{1}{N}\sum x_i^2}$；
   - 若帧能量与上一帧差异较小，以权重平滑更新底噪基底 `noiseFloor`（区间钳位在 0.002 ~ 0.06）。
4. **机械敲击与瞬态脉冲过滤**：
   - 计算前半帧能量 $E_{front}$ 与后半帧能量 $E_{back}$ 的比值 $R_{impulse} = \frac{E_{front} + 10^{-5}}{E_{back} + 10^{-5}}$；
   - 若 $R_{impulse} > 3.5$（突然大幅增大）或 $R_{impulse} < 0.28$（突然大幅衰减），判定为键盘敲击、鼠标点击等机械瞬态脉冲，予以剔除。
5. **波峰因数过滤**：
   - 计算 $CrestFactor = \frac{Peak}{RMS}$；
   - 若波峰因数 $< 1.55$，判定为平直正弦蜂鸣或稳态底噪，予以剔除。
6. **自相关基频周期性检验（Pitch Detection）**：
   - 计算自相关函数 $R(\tau) = \frac{\sum x_i x_{i+\tau}}{\sqrt{\sum x_i^2 \sum x_{i+\tau}^2}}$；
   - 搜索滞后量区间固定为 $\tau \in [45, 140]$ 采样点；
   - 对应发声频率 $f = \frac{16000}{\tau} \in [114\text{Hz}, 355\text{Hz}]$，完全覆盖正常人类说话基频；
   - 必须保持 16kHz 时域与 256 点 Buffer 的数学一致性，严禁随意在小 Buffer 下按更高采样率缩放滞后量，防止 Lag 越界引发阵列截断与噪声误触发。
7. **多帧防抖确认**：
   - 只有在同时满足能量门限、自相关系数 $\ge 0.38$、非机械脉冲、非单音时，`consecutiveSpeechFrames` 计数加 1；
   - 连续满足 3 帧（约 48ms）才确认触发，随即调用 `suspend()` 自行静默并向上通知控制器。

## 5. 原生音频录制与信号降噪处理 (`modules/voice/audioRecorder.js` & `wavAudioEncoder.js`)

右键点击麦克风时，启动独立录音链路，产物直接作为附件发送。为了彻底消除风扇风噪、环境白噪与前置放大器底噪，同时保证人声不发生机械金属变调，构建了三道声学过滤链：

### 5.1 拾音硬件层控制（保留自然人声）
在 `navigator.mediaDevices.getUserMedia` 参数配置中：
- `noiseSuppression: true`：借用 WebRTC 内核原生稳态噪声抑制算法，在输入源头过滤房间空调流通与电脑风扇的基础嗡嗡声；
- `autoGainControl: false`：**强制关闭自动增益**，彻底避免 AGC 算法在停顿时盲目拉升前置放大器本底噪声、说话时产生金属机械感与合成音失真。

### 5.2 80Hz Butterworth 二阶高通滤波器 (`applyHighpassFilter`)
人类正常说话的发声基频一般均在 85Hz 以上，而电脑机箱散热风扇震动、桌面机械共振及空调气流多集中在 30Hz ~ 80Hz 次低频区：
- 采样点流经精确计算的二阶巴特沃斯高通数字滤波器，截止频率设定为 80Hz（Q = 0.7071）；
- 在频域上对 30Hz~60Hz 杂音实现高达 70% 以上的物理衰减，彻底净化低频听感基底。

### 5.3 停顿区软噪声门控 (`applySoftNoiseGate`) 与首尾静音裁剪 (`trimSilenceAndFade`)
1. **有效发声区间检测**：
   - 以 20ms 为窗口计算 RMS 能量曲线；
   - 提取 15% 分位数为背景噪声门限，90% 分位数为语音峰值；
   - 自适应阈值设定为 $T = NoiseFloor + 0.2 \times (SpeechPeak - NoiseFloor)$；
   - 双向扫描确定首个有效发声帧 `firstSpeechFrame` 与最后一个有效发声帧 `lastSpeechFrame`。
2. **前后余量补全与首尾余弦淡入淡出**：
   - 起始端向前保留 100ms 缓冲区（Pre-roll），防止吞掉轻辅音；
   - 结尾端向后保留 150ms 缓冲区（Post-roll），保留尾部自然余韵；
   - 首部 20ms 与尾部 30ms 施加升余弦衰减因子，彻底避免音频截断处的爆音。
3. **停顿区平滑软噪声门（Soft Noise Gate）**：
   - 针对用户在句子中间停顿、换气（如 00:07、00:15 处）时容易暴露话筒沙沙底噪的问题；
   - 逐帧计算能量：低于门限时，目标增益衰减至 0.10（约 -20dB 压制）；高于门限时全通放行（增益 1.0）；
   - 采用 5ms 极速 Attack（不吃首音节）与 60ms 平滑 Release（平滑衰减无台阶爆音），使中间停顿区如录音棚般安静沉寂。

### 5.4 裸 PCM 编码为标准 RIFF WAV (`encodeWav`)
不依赖任何外部编译包，直接在前端分配连续 `ArrayBuffer`：
- 严格遵循 RIFF 规范构造 44 字节头部：`RIFF` 标识、文件大小、`WAVE` 标识、`fmt ` 块（单声道、16-bit 深度、目标采样率）、`data` 块；
- 将 Float32 PCM 归一化为有符号 16 位整数（$-32768 \sim 32767$）填充入缓冲区，生成 `audio/wav` 类型的二进制 Blob。

### 5.5 附件管道无缝融合
录音停止后生成文件名（如 `audio_record_20260929_143000.wav`），调用 `electronAPI.handleFileDrop(agentId, topicId, [fileData])`：
- 完全复用现有的附件存储、缩略预览与上下文装配机制，无多余私有协议。

## 6. 口令短语匹配与流式状态互斥 (`modules/voice/speechDirectiveMatcher.js`)

支持用户自定义“清空”、“发送”快捷短语，识别文本时自动提取语义并执行动作。

### 6.1 短语解析与匹配逻辑
- **多短语切分**：`parseCommaPhrases` 同时兼容中文逗号（`，`）与英文逗号（`,`），自动去除项首尾空格并剔除空项；
- **正则安全转义**：对短语进行 `escapeRegex` 转义，防止标点字符引起正则崩溃；
- **优先级保障**：**清空指令（CLEAR）严格优先于发送指令（SEND）**，只要命中清空词立即清空草稿；
- **标点剥离**：命中发送短语时，正则自动清除短语前后的标点符号（`，,。！!？?、；;~～\s*`），保留干净的用户意图文本。

### 6.2 AI 流式吐字期间的互斥保护
当用户说了发送词，而 AI 正在流式输出时，存在巨大隐患：若排队等 AI 吐完再发，用户在此期间对输入框进行修改会导致半截草稿被误发。
系统采取以下确定性防御策略：
1. **流式状态判定**：实时检查发送按钮状态 `sendMessageBtn?.dataset?.mode === 'interrupt'`；
2. **短语屏蔽**：
   - 若处于中断/流式输出模式，传入匹配器的 `sendDirectives` 强制置空；
   - 识别文字中的“发送”等词汇**不作为指令响应，既不发送，也不从文本中剔除**，作为普通文字完整保留在输入框中；
   - 清空短语不受此影响，用户仍可随时清空重置；
3. **按钮点击双重校验**：在任何情况下执行发送动作时，必须满足 `btn && !btn.disabled && btn.dataset?.mode !== 'interrupt'`，绝对不触发中断停止动作。

## 7. 主进程调度与跨窗口避让协调

### 7.1 主聊天语音协调器 (`MainChatVoiceCoordinator`)
主进程中负责主聊天听写会话的生命周期管理：
- **自律避让**：在 `startSession` 启动时，先检查独立语音小窗口是否正在听写（`isSubwindowHotkeyActive()`）。若正在听写，返回 `{ success: false, reason: 'subwindow_active' }`，前端捕获后弹出 Popover 气泡提示用户，主动放弃争抢；
- **文字沉淀加速（Settling）**：当跳板窗口上报 `settled: true` 时，将原本 50ms 的结算等待加速为 10ms，提高交互跟手度；
- **空闲超时与静音防抖**：未发声超时（默认 5.5s）与说话后静音超时（默认 2.5s）支持在全局设置中灵活配置；
- **生命周期绑定**：主窗口 `webContents` 销毁时，自动调用 `cancelSession()`，释放底层 Rust 引擎热键和临时跳板窗口。

### 7.2 物理快捷键抢占逻辑（彻底退出模式）
当主聊天正在听写时，若用户在独立小窗口按下了全局快捷键 F7：
- 主进程调度中心通过 `mainChatVoiceCoordinator.cancelSession({ reason: 'hotkey_preempted' })` 撤销主聊天会话；
- 主聊天前端接收到通知后执行 `deactivateSttMode()`：麦克风呼吸灯熄灭、人声哨兵彻底注销，**完全等同于用户手动点击按钮退出**，绝无残留监听。

### 7.3 修复原作者底层临时跳板窗口悬挂缺陷
- **问题排查**：原作者代码中，若用户按下 F7 后一句话没说，点击屏幕导致 Win+H 停止，随后直接关闭语音聊天小窗口，`voiceCaptureWindow` 会永久卡死在屏幕右下角无法关闭。
- **精准属主销毁**：
  在 `modules/ipc/voiceHandlers.js` 的 `voiceChatWindow.on('closed')` 中，建立精准属主判定：
  ```javascript
  if (voiceCaptureSession && voiceCaptureSession.target === voiceChatWindow) {
      cancelVoiceCaptureFromHotkey().catch(() => {});
  }
  ```
  - 仅当当前活跃的快捷键会话确实服务于被关闭的这个窗口时，才清理该会话并隐藏跳板窗口；
  - 若临时跳板窗口正服务于主界面，小窗口的关闭不会对其产生任何误杀。
